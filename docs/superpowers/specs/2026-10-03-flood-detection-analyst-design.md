# ตรวจจับน้ำท่วมรายกล้องและหน้า Analyst

วันที่: 2026-10-03

## เป้าหมายและขอบเขตที่ผู้ใช้ยืนยัน

เพิ่มการตรวจจับจากภาพกล้องจริง พร้อมเก็บผลย้อนหลัง และแยกเมนู Analyst สำหรับกราฟ ผู้ใช้เลือกการประมวลผลบนเครื่องหรือเซิร์ฟเวอร์ที่เปิดต่อเนื่องตามแบบที่เสนอ และตอบรับแบบในบทสนทนาด้วย “ok”

ผลสำเร็จคือกล้องแต่ละตัวมีผลวิเคราะห์ล่าสุดและเวลาตรวจ ผู้ใช้เปิดภาพหลักฐานได้ และดูประวัติผ่านกราฟที่มีตัวกรองกล้อง ทางแยก และช่วงเวลา ผลมาจากภาพจริงเท่านั้น ข้อมูลสังเคราะห์ใช้เฉพาะการทดสอบที่แยกจากฐานข้อมูลใช้งาน

ระบบมีความสามารถวิเคราะห์ครบ 40 รหัสกล้อง แต่แต่ละกล้องต้องกำหนดและตรวจบริเวณถนนที่เฝ้าระวังก่อนเปิดการจัดสถานะ ไม่ถือว่าทุกกล้องพร้อมใช้งานเพียงเพราะอ่านสตรีมได้

## สภาพระบบปัจจุบัน

- เว็บ HTML/CSS/JavaScript และ hls.js มีรายชื่อกล้องใน `scripts/data.js`
- มี 40 รหัสกล้องที่ไม่ซ้ำใน 10 กลุ่ม รหัส 13 และ 14 อยู่มากกว่าหนึ่งกลุ่ม ต้องประมวลผลและนับเพียงครั้งเดียวต่อรหัส
- เว็บเล่นเฉพาะกล้องที่อยู่บนจอ และพักเมื่อไม่มีคนดู จึงใช้การเปิดเว็บเป็นตัวขับการวิเคราะห์ต่อเนื่องไม่ได้
- `tools/build.cjs` สร้างเว็บ static ใน `dist/` และ `vercel.json` ใช้โฮสต์เว็บชุดนี้ ยังไม่มี API หรือฐานข้อมูล
- เครื่องพัฒนามี Python 3.11, PyTorch, OpenCV, FastAPI และ Uvicorn แต่ยังไม่มี Transformers หรือ FFmpeg ใน PATH จากการตรวจครั้งนี้

## ทางเลือกและการตัดสินใจ

เลือกบริการ Python ที่ประมวลผลเองและเก็บ SQLite บนดิสก์ถาวร เริ่มรันบนเครื่องพัฒนาและเตรียม Docker สำหรับเครื่องที่เปิดต่อเนื่อง เว็บเดิมเรียก API อ่านผล ไม่มีค่าบริการ AI ต่อภาพจากทางเลือกนี้ แต่ยังต้องจัดหาเครื่องและทรัพยากรประมวลผล

ทางเลือกส่งภาพให้บริการ AI ภายนอกลดภาระดูแลโมเดล แต่ต้องกำหนดผู้ให้บริการ API key และค่าใช้บริการ จึงไม่อยู่ในรอบแรก การประมวลผลในเบราว์เซอร์อย่างเดียวไม่ตอบโจทย์การเก็บผลแม้ปิดเว็บ

## ส่วนประกอบและการไหลของข้อมูล

1. **ทะเบียนกล้อง:** เครื่องมือ Node ส่งออกรหัส ชื่อ URL สตรีม และความสัมพันธ์กับกลุ่มจาก `CctvData` เป็น JSON สำหรับ backend ใช้รหัสไม่ซ้ำและมีการตรวจความตรงกับข้อมูลเว็บ
2. **ตัวดึงภาพ:** FFmpeg อ่าน HLS และส่งภาพนิ่งหนึ่งภาพ มีเวลาหมดอายุของแต่ละคำสั่ง ไม่เปิดสตรีมทั้งหมดค้างไว้ ใช้ argument list โดยไม่ผ่าน shell และรับ URL จากทะเบียนกล้องเท่านั้น
3. **ตัววิเคราะห์:** โหลดโมเดลครั้งเดียว วิเคราะห์ภาพนิ่ง และส่ง mask พื้นที่น้ำกับคะแนนโมเดล
4. **ตัวจัดสถานะ:** คำนวณเฉพาะบริเวณถนนที่กำหนด ตรวจคุณภาพข้อมูลและใช้ผลต่อเนื่องลดสถานะกระพริบ
5. **ตัวเก็บข้อมูล:** บันทึก observation และเหตุการณ์พร้อมข้อมูลรุ่นโมเดล รุ่นการตั้งค่า และเวลาลง SQLite
6. **API:** ให้ผลล่าสุด ประวัติ กราฟ ภาพหลักฐาน และการตั้งค่าที่ต้องยืนยันสิทธิ์
7. **เว็บ:** แสดงสถานะบนรายกล้องและหน้า Analyst โดยไม่ต้องเปิดวิดีโอเพื่ออ่านประวัติ

บริการ API และ worker เป็นคนละ process ใช้ SQLite WAL และ transaction สั้น เพื่อไม่ให้การวิเคราะห์ภาพบล็อกการอ่านกราฟ มีคำสั่งเริ่มระบบที่ชัดเจนและ Docker Compose สำหรับใช้งานบนเครื่องต่อเนื่อง ไม่ deploy ระบบจริงในขั้นตอนพัฒนา

## โมเดลและนิยามผลตรวจ

เริ่มด้วย adapter สำหรับ `facebook/mask2former-swin-tiny-ade-semantic` ผ่าน Transformers/PyTorch ซึ่งเป็นโมเดลแยกพื้นที่ภาพทั่วไปบน ADE20K ไม่ใช่โมเดลที่ผ่านการรับรองการตรวจน้ำท่วมจากกล้องฉะเชิงเทรา

โหลดน้ำหนักที่ฝึกแล้วเท่านั้น ใช้ safetensors และไม่เปิด `trust_remote_code` ต้องตรึง revision ที่ดาวน์โหลดได้จริง ตรวจแหล่งน้ำหนักและเงื่อนไขการใช้งานก่อนติดตั้ง และบันทึก revision ในทุกผล การเปลี่ยนโมเดลเป็นการตั้งค่า adapter โดยไม่เปลี่ยนสัญญา API หากน้ำหนักหรือ label ที่ต้องการใช้ไม่ได้ ให้ระบบแสดง model unavailable แทนการสร้างผลทดแทน

อ่านชื่อ label จาก config และจัดกลุ่ม water/river/sea/lake ที่โมเดลรองรับ คำนวณ semantic probabilities จาก output และ mask ตามขนาดภาพจริง ให้บริเวณถนนที่ผู้ใช้กำหนดตัดท้องฟ้า แม่น้ำ และสิ่งแวดล้อมที่ไม่ต้องเฝ้าระวังออก

ค่าที่รายงานคือ **สัดส่วนพื้นที่น้ำที่โมเดลตรวจพบในบริเวณเฝ้าระวัง (%)** โดยนับ pixel น้ำที่ผ่านเกณฑ์คะแนนโมเดลหารด้วยจำนวน pixel ทั้งบริเวณ ไม่เรียกคะแนนโมเดลว่าความแม่นยำที่พิสูจน์แล้ว และไม่แปลงเป็นความลึกเซนติเมตร

เกณฑ์เริ่มต้นที่ปรับรายกล้องได้:

- คะแนน pixel น้ำขั้นต่ำ 0.50
- สัดส่วนน้ำตั้งแต่ 5% แต่ต่ำกว่า 15%: “สงสัยน้ำท่วม”
- ตั้งแต่ 15% ติดต่อกัน 3 ผลที่ใช้งานได้: “พบต่อเนื่อง” ก่อนครบให้เป็น “สงสัยน้ำท่วม”
- ต่ำกว่า 5%: “ไม่พบน้ำในภาพ” สำหรับกล้องที่ไม่ได้อยู่ในสถานะพบต่อเนื่อง
- เมื่อเคยพบต่อเนื่อง ต้องต่ำกว่า 5% ติดต่อกัน 3 ผลจึงกลับเป็นไม่พบ ระหว่างรอยืนยันการลดลงแสดงสถานะเดิมพร้อมค่าล่าสุด
- ผลขาดช่วงเกิน 180 วินาที ผลผิดพลาด การเปลี่ยน ROI หรือการเปลี่ยนรุ่นโมเดล/เกณฑ์ ตัดการนับผลต่อเนื่อง

ค่าข้างต้นเป็นเกณฑ์เริ่มประเมิน ไม่ใช่ข้ออ้างว่าระบบแม่นยำแล้ว ภาพมืดจนอ่านไม่ได้ ภาพว่าง สตรีมค้างที่ยืนยันได้จากลำดับ playlist ไม่เปลี่ยน ผลโมเดลผิดรูปแบบ และ ROI ใช้ไม่ได้ ต้องเป็น “วิเคราะห์ไม่ได้” โดย metric เป็น null ภาพนิ่งที่บังเอิญเหมือนเดิมไม่เพียงพอจะสรุปว่าสตรีมค้าง

## การตั้งค่ารายกล้อง

เพิ่มหน้าตั้งบริเวณเฝ้าระวังที่เข้าจากรายละเอียดกล้องได้ ดึง snapshot จริง แสดงเครื่องมือวาด polygon พิกัด normalized 0–1 พร้อมตัวอย่าง ROI และแก้เกณฑ์รายกล้อง ตรวจ polygon ว่าไม่ไขว้ มีพื้นที่ และอยู่ในภาพ

กล้องที่ยังไม่ตั้งค่าแสดง “ยังไม่กำหนดบริเวณตรวจ” และไม่สร้างผลไม่พบน้ำอัตโนมัติ การบันทึกการตั้งค่าใช้ admin token ฝั่งเซิร์ฟเวอร์ ผู้ใช้กรอกในหน้าตั้งค่า token อยู่ในหน่วยความจำของแท็บเท่านั้น ไม่บันทึกใน localStorage และไม่ใส่ใน URL

การตั้งค่าทุกครั้งเพิ่ม config revision และล้างลำดับยืนยันของกล้อง ประวัติเก่าเก็บ revision เดิมเพื่ออธิบายการเปลี่ยนแปลงของกราฟ

## รอบการทำงานและข้อผิดพลาด

- ตั้งเป้า 60 วินาทีต่อกล้อง ใช้ capture concurrency ไม่เกิน 2 และ inference ทีละภาพ เริ่มด้วย CPU และรองรับ GPU เมื่อมี
- แต่ละ capture หมดอายุภายใน 20 วินาที และยุติ child process พร้อมเก็บสาเหตุ เมื่อไม่มี FFmpeg ให้ health รายงาน dependency missing
- รอบถัดไปไม่ซ้อนงานกล้องเดิม ไม่ไล่ทำคิวเก่าจนสะสม API รายงานเวลาในคิว เวลาตรวจล่าสุด และรอบที่ทำได้จริง
- โหลดโมเดลใน worker ที่แยกจาก API จำกัดเวลาการวิเคราะห์ต่อภาพ หากค้างให้ worker supervisor ยุติและเริ่มใหม่พร้อมสถานะ model error
- ใช้เวลาที่จับภาพเป็นเวลาผล และเก็บเวลาเสร็จต่างหาก ถ้า inference เสร็จช้าจนผลเก่าเกิน 180 วินาที ไม่ใช้เปลี่ยนสถานะปัจจุบัน
- เก็บเวลาต้นทาง HLS เมื่อมี program date time และแสดงว่าไม่มีเวลาต้นทางเมื่อไม่มี ไม่อ้างว่าเวลาจับภาพยืนยันว่าเหตุการณ์เกิดตรงเวลานั้น
- ปิดระบบอย่างเรียบร้อย ยุติ child process และ flush transaction หลัง restart สถานะเก่าต้องผ่าน freshness check และเริ่มนับความต่อเนื่องใหม่

## ฐานข้อมูลและการเก็บรักษา

ตารางหลักคือ camera_configs, observations และ events พร้อม schema version/migration ที่ไม่ทำข้อมูลเดิมหาย observation เก็บ camera_id, captured_at, processed_at, source_at เมื่อมี, status, reason, water_coverage_pct หรือ null, model_score หรือ null, model_id/revision, config_revision และ evidence_id เมื่อมี

เก็บ observation 30 วันและภาพหลักฐาน 7 วันเป็นค่าเริ่มต้น ปรับได้ด้วยการตั้งค่าเซิร์ฟเวอร์ เก็บภาพล่าสุดหนึ่งชุดต่อกล้องสำหรับตั้งค่า และเก็บภาพเริ่ม/สิ้นสุดเหตุการณ์พร้อม mask ของผลที่ก่อเหตุการณ์ ลดการเก็บภาพทุกนาทีโดยไม่จำเป็น

แยก observation ของการวิเคราะห์ไม่ได้จากเหตุการณ์ที่พบต่อเนื่อง ไม่ปิดเหตุการณ์เป็นปลอดน้ำเพียงเพราะสัญญาณหาย แต่บันทึกช่วงสิ้นสุดการเฝ้าระวังที่เชื่อถือได้และสาเหตุ เมื่อกลับมาได้ต้องเริ่มยืนยันใหม่

ฐานข้อมูล น้ำหนักโมเดล snapshot และ token อยู่นอก `dist/` และ git ใช้ directory ที่กำหนดและ persistent Docker volume การลบตาม retention จำกัดอยู่ใน directory หลักฐานที่ตรวจ resolved path แล้ว ภาพหมดอายุแสดง “ภาพหลักฐานหมดอายุ” แต่ประวัติผลยังอ่านได้จนถึงกำหนดของ observation

## API และการเข้าถึง

- `GET /api/flood/health`: สถานะ API, worker, model, dependencies, รอบงาน และ freshness
- `GET /api/flood/cameras`: ผลล่าสุดต่อรหัสกล้อง สถานะ effective หลังตรวจอายุ พร้อมสาเหตุ
- `GET /api/flood/cameras/{id}/history`: ประวัติที่แบ่งหน้าและจำกัดช่วงเวลา
- `GET /api/flood/analytics`: time buckets ตามกล้อง/กลุ่ม/เวลา พร้อมจำนวน valid, unknown และ monitored cameras
- `GET /api/flood/events`: เหตุการณ์ที่แบ่งหน้าและมีตัวกรองเดียวกับกราฟ
- `GET /api/flood/evidence/{evidence_id}`: ภาพ/overlay จาก ID ที่บันทึกในฐานข้อมูล ไม่รับ file path จาก client
- `GET /api/flood/cameras/{id}/config` และ `PUT` สำหรับอ่าน/บันทึก ROI; snapshot ตั้งค่าและการเขียนต้องมี admin token

ตรวจ camera_id จากทะเบียน พารามิเตอร์เวลา/จำนวนผลด้วย schema จำกัดจำนวนและช่วง query ไม่ปล่อย arbitrary SQL, arbitrary stream URL หรือ arbitrary path CORS อนุญาตเฉพาะ origin ที่ตั้งค่า ค่าเริ่มต้น backend bind localhost การเปิดบนอินเทอร์เน็ตต้องใช้ reverse proxy HTTPS และ origin ที่ตรงกับเว็บ

เว็บกำหนด API base URL จากไฟล์ config สาธารณะที่ไม่มี secret ค่าเริ่มต้นเชื่อมบริการ local เพื่อพัฒนา เว็บ static ที่โฮสต์แยกใช้ HTTPS API ที่ผู้ดูแลระบุ อ่าน health เมื่อเปิดหน้าและ polling ผลล่าสุดทุก 15 วินาที พัก polling เมื่อแท็บซ่อน ยกเลิก request เก่าเมื่อเปลี่ยนตัวกรอง

## หน้ากล้องและ Analyst

เพิ่ม navigation “กล้องสด” และ “Analyst” ใช้ธีม ภาษาไทย และ responsive layout เดิม หน้า Analyst มี URL hash เพื่อ refresh/deep link โดย hash เดิม `#test` ยังทำงาน

รายกล้องแสดง badge ผลน้ำแยกจากสถานะการเล่นวิดีโอ เวลาและ metric ล่าสุด แตะเพื่อเปิดรายละเอียด ภาพหลักฐาน และลิงก์ไปประวัติของกล้องนั้น กล้องข้อมูลเก่า/API ขัดข้องต้องแสดงวิเคราะห์ไม่ได้พร้อมอายุข้อมูล

หน้า Analyst ประกอบด้วย:

- ตัวกรองกล้อง/ทางแยก และ 1 ชั่วโมง/24 ชั่วโมง/7 วัน/30 วัน
- สรุปจำนวนกล้องพบต่อเนื่อง สงสัย วิเคราะห์ได้ และวิเคราะห์ไม่ได้ ตามขอบเขตที่เลือกและรหัสไม่ซ้ำ
- กราฟสัดส่วนพื้นที่น้ำรายกล้องพร้อมแกน % เวลาไทย และตัวเลขค่าเฉลี่ย/สูงสุดของแต่ละ bucket ที่ระบุวิธีคำนวณชัดเจน
- กราฟจำนวนกล้องพบต่อเนื่องตามเวลา พร้อมจำนวนกล้องที่มีข้อมูลใช้งานได้เป็นตัวเทียบ
- รายการเหตุการณ์ เวลาเริ่ม/สิ้นสุดหรือช่วงข้อมูลขาด กล้อง ค่า peak และภาพหลักฐานเมื่อยังมี
- ตารางข้อมูลที่อ่านด้วย screen reader ได้ควบคู่กับ SVG chart

ข้อมูลขาดแสดงช่องว่าง กราฟไม่ลากเส้นผ่าน bucket ที่ไม่มี valid observation ไม่แทน null ด้วย 0 bucket ของจำนวนกล้องใช้ผลล่าสุดที่ยัง fresh ต่อกล้อง ณ ปลาย bucket และไม่เอาค่าปัจจุบันไปใส่ประวัติ หากเลือกทุกกล้อง กราฟสัดส่วนพื้นที่น้ำให้ผู้ใช้เลือกกล้องเพื่อแสดงรายละเอียด ไม่เฉลี่ยภาพคนละมุมเป็นระดับน้ำรวม

เมื่อเข้า Analyst ให้หยุด auto tour และปล่อย player ของกล้องสด เมื่อกลับมาคืนกล้อง/หน้าเดิม แต่ไม่เปิด tour อัตโนมัติเอง รองรับ loading, empty history, API unavailable, model unavailable, partially configured และ stale data โดยข้อความไม่สื่อว่าพื้นที่ปลอดน้ำเพราะไม่มีข้อมูล

## การทดสอบและเกณฑ์ส่งมอบ

1. Regression ของเว็บเดิมต้องผ่าน รวม player cleanup, search, favorites, mobile swipe และ static packaging ที่ปรับ allowlist ให้ตรงไฟล์ใหม่
2. Unit tests ครอบคลุม mask/ROI, polygon, null, threshold boundaries, consecutive confirmation, freshness, revision changes และการนับรหัสซ้ำ
3. Integration tests ใช้ SQLite temporary database ยืนยัน persistence หลัง restart, retention, pagination, bucketing, timezone, gap handling, token, CORS และการจำกัด query
4. Worker tests ยืนยัน timeout, queue ไม่ซ้อน, dependency/model failures และไม่มีการสร้าง synthetic observation ใน production path
5. Browser tests ตรวจ navigation, per-camera badge, filters, graph/table agreement, unknown/stale/offline, ROI editor, player release และหน้าจอ 320/390/768/1440 px
6. Live check ดึงภาพ ITIC จริง วิเคราะห์ด้วยน้ำหนักที่ฝึกแล้วของโมเดล เก็บ timestamp/รุ่น/เวลา inference และยืนยันข้อมูลอ่านกลับจาก API และหน้า Analyst หลัง restart แยกจากผลทดสอบจำลอง
7. ประเมิน latency ของรอบ 40 กล้องบนเครื่องนี้และรายงาน cadence ที่ทำได้จริง ไม่อ้างว่าทุกกล้องทำได้ทุก 60 วินาทีจนมีผลวัด
8. ตรวจภาพกับ mask/ROI ที่มนุษย์อ่านได้อย่างน้อยหนึ่งกล้องที่กำหนดบริเวณแล้ว การไม่มีภาพน้ำท่วมจริงในวันทดสอบไม่เป็นหลักฐานว่าโมเดลตรวจน้ำท่วมได้แม่นยำ ต้องรายงานขอบเขตการประเมินตามจริง

การส่งมอบรอบนี้คือระบบที่รันได้จริง คู่มือเริ่มเครื่อง/ตั้งกล้อง/ต่อเว็บ/สำรองข้อมูล ตัวอย่าง config ที่ไม่มี secret และหลักฐานตรวจ live pipeline การยืนยันความแม่นยำใช้งานจริงต้องมีภาพอ้างอิงที่ติด label ทั้งน้ำท่วม ถนนแห้ง ถนนเปียก ภาพกลางคืน และภาพสะท้อนจากมุมกล้องเหล่านี้ แยกรายงาน precision/recall และ false alerts ออกจากความสำเร็จในการเดินระบบ

## ขอบเขตที่ไม่รวม

ไม่ทำการแจ้งเตือนภายนอกอัตโนมัติ ไม่เพิ่มค่าความลึกน้ำ ไม่เก็บวิดีโอตลอดเวลา ไม่ฝึกโมเดลเฉพาะพื้นที่โดยไม่มีชุดภาพติด label และไม่เปิดบริการสาธารณะหรือ deploy production อัตโนมัติ
